## Deviations and decisions

| # | Area | Deviation | Why | Action for the lead / WP8 |
| --- | --- | --- | --- | --- |
| 1 | Extra file | Added `scripts/3d/arena_ground_tiles.gd`, not on the WP7 file list. | `ground_tile.glb` has no way to place one visual-only tile: both variants (`GroundTile_A`/`GroundTile_B`) each import their own `StaticBody3D` collider on layer 1 (confirmed empirically), and stripping a collider from an already-instanced sub-scene's children is not something raw `.tscn` text can do reliably (Godot's "editable children" override mechanism is an editor-authored feature; there is no worked example of it anywhere in this repo to copy). This small, arena-specific script instances one 4 x 2 m A/B pair per two columns (`ground_tile.glb` already holds the pair 2 m apart, docs/deviations/wp1.md #8), frees every imported `StaticBody3D` it finds so a tile contributes a `MeshInstance3D` only, and flips alternate rows 180 degrees about Y so the fixed A-left/B-right pair reproduces a true two-axis checkerboard. It never touches `NavigationRegion3D` (the tiles are a sibling of it), so even before the collider-stripping the glb's colliders could never have reached the navmesh bake. | None; kept inside `scripts/3d/`, arena-specific, does not touch any shared file. |
| 2 | `_cache_blocked_cells_from_props()` mismatch | WP4's helper (`main_3d.gd`) expects each prop's **direct child** under `NavigationRegion3D` to itself be a `CollisionObject3D` holding a `BoxShape3D`. The real assets nest their collider two levels down instead (confirmed empirically by instancing each model and printing its tree: `Tree/Tree_Body/Tree_Col`, `Crate/Crate_Body/Crate_Col`, `Chest/Chest_Body/Chest_Col`, `GroundTile/GroundTile_A/GroundTile_A_Col`), and the collider's shape is a `ConcavePolygonShape3D` (a baked trimesh), never a `BoxShape3D`. So `blocked_cells` (the 2D-style `AStarGrid2D` cache) never marks a tree/crate/chest footprint solid in this arena. | WP1's asset export (docs/deviations/wp1.md #3, `-colonly`) and WP4's helper (docs/3d-port-contracts.md section 9) were written independently and never cross-checked against each other's actual node depth/shape type. `main_3d.gd` is off-limits to this package (contracts, "stay inside the files your work package owns"). | Verified this has no functional impact on movement: `_request_player_turn_move_by_distance` / `_request_enemy_turn_move_by_distance` route through `_build_world_path_from_navigation`, which calls `NavigationServer3D.map_get_path` on the baked navmesh directly and never reads `blocked_cells`; `_is_player_position_blocked` queries the physics server live (layer mask, not the cache) and also picks up the real colliders correctly. The only consumer of `blocked_cells`/`astar_grid` for prop avoidance is `_spawn_additional_enemy`'s nearest-walkable-cell search, which this arena's fixed, pre-placed enemies never call. If a future package starts using `_spawn_additional_enemy` near a prop, either widen `_cache_blocked_cells_from_props` to walk descendants (like `prop_3d.gd` does) instead of direct children, or accept that a spawned enemy may land inside a prop's footprint on the legacy grid (the navmesh and physics will still keep it from clipping through, since baking/collision are unaffected). |
| 3 | Offline bake tool startup hook | `tools/bake_arena_navmesh.gd` cannot `load()` `arena.tscn` from `_init()`: it fails with `Compile Error: Identifier not found: StoryBook`, the same failure `--check-only --script` hits on `main_3d.gd` (docs/deviations/wp4.md #1), but this time on a plain `--script` run. Godot's `-s/--script` mode replaces the main loop with the given script *before* `SceneTree`'s own initialization (which registers the project's autoloads) has run; `_init()` (the GDScript constructor) fires too early to see them, so any scene whose script resolves an autoload by bare identifier at compile time fails to `load()`. | Godot 4.7.2 behaviour on this project's `--script` path, not a script fault. | Fixed by moving the load/instance/bake logic into the `MainLoop._initialize()` override instead of `_init()`; `_initialize()` runs after `SceneTree` has registered autoloads, so `arena.tscn` (and `main_3d.gd`'s `CombatFx`/`StoryBook`/`LootMenu`/`ItemFactory`/`LootDropper` references) load normally. With that fix the synchronous bake (`NavigationRegion3D.bake_navigation_mesh(false)`) worked on the first attempt; the "fall back to an empty mesh" contingency in the package brief was not needed. Also sets `bake_navmesh_if_empty = false` on the freshly instantiated arena (via `Node.set`, not by editing the committed scene) so the coordinator's own `_ready()` does not start a second, threaded bake on the same `NavigationRegion3D` the moment it is added to the tree, racing this tool's synchronous one. |
| 4 | Navmesh: baked and shipped | `scenes/3d/arena_navmesh.tres` is a real baked mesh (181 polygons, `geometry_parsed_geometry_type = 1`, `geometry_collision_mask = 9`, `agent_height = 2.0`, default `cell_size`/`agent_radius` matching the requested 0.25/0.5), referenced from `arena.tscn` as `navigation_mesh = ExtResource(...)`. `bake_navmesh_if_empty` is left at its script default (`true`) on the committed arena root, so if the mesh is ever cleared again (e.g. re-baked with a bad geometry mask), WP4's runtime-bake fallback still applies automatically; nothing in the committed scene depends on the export being `false` (that override only ever lives transiently inside the bake tool's own in-memory instance). | Task requirement, "try to ship a baked mesh". | Re-run `& $godot --headless --path $wt --script res://tools/bake_arena_navmesh.gd` and re-stage `scenes/3d/arena_navmesh.tres` whenever the level layout changes. |
| 5 | Layout choices | 24 x 24 m clearing; 20 trees on a ring of radius 13 m (18 degrees apart, chord ≈ 4.07 m between trunk centres, ≈ 3.5 m gap between the ≈ 0.46 m-wide trunk colliders, i.e. one gate roughly every 18 degrees, comfortably inside the requested 2-4 m); crate at `(3, 0, 3)`, `TreasureChest` (chest.glb) at `(3, 0, -3)`, both near the centre; `Spawn_default` at `(-9, 0, 0)`, one map-edge inside the ring; three `stub_enemy_3d` instances at `(0,0,0)`, `(-2,0,5)`, `(-2,0,-5)` (8.6-9 m from the spawn). Ground tiling extended to 14 x 14 tiles (28 x 28 m) rather than exactly 24 x 24 m, so the checkerboard floor also covers the tree ring itself with no bare-earth gap between the nominal clearing edge and the ring; the `Ground` `StaticBody3D`'s `BoxShape3D` is sized to match (30 x 0.4 x 30 m, top at y = 0) and carries no visible mesh (the tiles are the only floor visual, avoiding z-fighting with a second flat surface at the same height). | Reasoned from the actual, empirically measured collider/mesh sizes (tree trunk collider ≈ 0.46 x 0.46 m footprint, crate/chest footprints from `tools/blender/generate_props.py`) rather than the visual canopy size, and from wanting no visible seam past the ring. | None; purely a level-design choice within this package's own file. |
| 6 | Story chapter | `story_chapter_id = &""` on the arena root, matching WP4's own `main3d_stub_arena.tscn` override, so `StoryBook.show_chapter_once()` no-ops instead of opening the prologue book every headless run. | Keeps the smoke test deterministic and matches existing WP4 precedent (contracts section 9, "Implemented in WP4"). | A future level-content package can set a real chapter id once the arena is used as an actual playable level rather than a WP7 deliverable. |
